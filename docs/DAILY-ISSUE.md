# 매일 한 편 — 나만을 위한 일간지

이 앱은 지금까지 **내가 넣은 것을 되돌려주는** 쪽이었다. 여기서부터 방향이
하나 더 생긴다. 매일 아침, 내가 넣지 않은 것이 올라온다.

재료는 노션 `My Identity` 페이지다. 거기 적혀 있던 관심사 29개가 주제 풀이
되고, 매일 하나가 뽑혀 한 편이 된다.

---

## 1. 왜 이게 필요한가

노션이 실패한 이유는 **복귀 동력이 없어서**였다. 내가 넣은 것만 들어 있는
서랍은 열 이유가 없다. 17개 항목이 전부 `Not started`로 석 달을 보낸 것이
그 증거다.

매일 한 편이 올라오면 이유가 생긴다. 어제 안 봤어도 오늘은 새 글이 있다.
그리고 그 글은 내 관심사에서 나왔으므로 남의 피드와 다르다.

---

## 2. 돌아가는 모양

```
노션 My Identity
      │  (한 번, 0015 마이그레이션)
      ▼
   topics  ──┐
             │   매일 06:18 KST
editor_notes ├──▶ GitHub Actions ──▶ Claude ──▶ posts (kind='auto')
  (요청·답)  │    daily-issue.ts                      │
             │                                        ▼
   최근 글 ──┘                              오늘 화면 + 웹푸시
```

### 왜 Vercel 크론이 아니라 GitHub Actions 인가

Vercel Hobby 함수는 **60초**에 끊긴다. 한 편을 제대로 쓰려면 그보다 걸린다.
Actions 는 시간 제한이 없고 이미 알림 틱 때문에 10분마다 깨어 있다.
크론도 Hobby 는 하루 1회 제한이 있어서 알림 엔진을 이미 Actions 로 옮겨둔
상태였다 — 같은 이유다.

### 주제를 고르는 규칙

1. **내가 요청한 것이 있으면 그것부터.** 사람이 시킨 것을 뒤로 미루는
   편집자는 없다. (`editor_notes.kind = 'request'`)
2. 없으면 가중치 뽑기. 다만 **최근에 나온 주제는 가중치를 깎는다** —
   7일이 지나야 제 무게를 회복한다. 같은 주제가 이틀 연속 나오면 그게 곧
   안 보게 되는 이유가 된다.

```
점수 = 무게 × min(1, 지난날수/7) × 난수(0.6~1.4)
```

## 3. 편집실 — 메일을 쓰지 않는 이유

처음에는 메일로 물어보려 했다(`hayoung.lee@softcamp.co.kr`). 그만뒀다.

**메일은 한 방향이다.** 발행기가 질문을 보낼 수는 있어도 답장을 받을 곳이
없다. 받으려면 메일 수신함을 폴링하는 장치를 또 만들어야 하고, 그건 이
서비스가 감당할 비용이 아니다.

그래서 묻는 곳과 답하는 곳을 **같은 자리**에 뒀다. `/editor` 다.

| 종류 | 누가 | 무엇 |
|---|---|---|
| `question` | 발행기 → 나 | 다음 호를 더 잘 쓰려고 묻는 것 |
| `request` | 나 → 발행기 | 내일 쓸 것을 지정 |
| `feedback` | 나 → 발행기 | 발행된 글에 대한 반응 |

답한 내용은 다음 호 프롬프트에 그대로 들어간다. 고리가 닫힌다.

알림은 이미 붙어 있는 **웹푸시**로 간다. 발행되면 폰에 뜨고, 누르면 그 글로
바로 들어간다. 메일보다 이쪽이 빠르다.

### 질문을 매번 하지 않는 이유

프롬프트에 *"세 번에 한 번이면 충분하다"* 고 적어뒀다. 매일 물으면 그것도
소음이 되고, 소음이 되면 편집실을 안 열게 된다. 알림 설계와 같은 원칙이다.

## 4. 켜는 법

### 4.1 마이그레이션과 시드

```bash
supabase/migrations/0015_daily_issue.sql   # topics · editor_notes · issue_runs
supabase/seed/0005_first_issue.sql          # 창간호 (이미 쓰여 있음)
```

`0015` 는 주제 29개를 자동으로 깔고, 신규 가입에도 트리거로 붙는다.
여러 번 돌려도 안전하다.

### 4.2 GitHub Actions 비밀값

저장소 `Settings → Secrets and variables → Actions` 에 넣는다.

| 이름 | 비고 |
|---|---|
| `ANTHROPIC_API_KEY` | **새로 필요하다.** console.anthropic.com 에서 발급 |
| `NEXT_PUBLIC_SUPABASE_URL` | 이미 쓰는 값 |
| `SUPABASE_SERVICE_ROLE_KEY` | 이미 쓰는 값 |
| `NEXT_PUBLIC_VAPID_PUBLIC_KEY` | 선택 — 없으면 푸시만 건너뛴다 |
| `VAPID_PRIVATE_KEY` | 선택 |
| `VAPID_SUBJECT` | 선택 |

### 4.3 손으로 한 번 돌려보기

Actions 탭 → `오늘의 한 편` → `Run workflow`.
`dry_run` 을 켜면 **저장하지 않고 글만 뽑아서 로그에 찍는다.** 처음에는
이걸로 톤을 확인하는 쪽을 권한다.

로컬에서도 된다.

```bash
ANTHROPIC_API_KEY=... \
NEXT_PUBLIC_SUPABASE_URL=... \
SUPABASE_SERVICE_ROLE_KEY=... \
ISSUE_DRY_RUN=1 \
node --experimental-strip-types scripts/daily-issue.ts
```

## 5. 비용

Claude Opus 5.5, effort `high`. 한 편에 입력 2~4천 토큰, 출력 3~5천 토큰쯤.
입력 $4/MTok, 출력 $20/MTok 기준으로 **한 편에 대략 $0.1 안팎**, 한 달이면
$3 정도다.

프롬프트의 고정부(문체 규약 + 독자 정보)에는 `cache_control` 을 걸어뒀다.
매일 같은 내용이므로 이틀째부터는 그만큼 싸진다.

비싸다고 느껴지면 `scripts/daily-issue.ts` 의 `MODEL` 을 `claude-sonnet-5-5`
로 바꾼다(입력 $2 / 출력 $10). 글의 밀도는 떨어진다.

## 6. 품질을 지키는 장치

| 위험 | 막는 법 |
|---|---|
| 같은 주제 반복 | 최근 7일 가중치 감쇠 + 최근 14편 제목을 프롬프트에 넣어 "겹치지 말 것" |
| 지어낸 사실 | 문체 규약에 *"확실하지 않으면 확실하지 않다고 쓴다"* 명시. 그래도 **사실관계는 확인하고 읽어야 한다** — 글 하단에 그렇게 적어뒀다 |
| 아는 것을 또 설명 | 독자 정보에 전공(Berklee 전자음악 · 체코어 · 부동산 · 보안)을 넣고 *"그 분야에서 기초를 설명하면 무례하다"* 고 못박음 |
| 목록으로 도망 | *"다섯 가지 방법 같은 글은 아무것도 남기지 않는다. 산문으로 쓴다"* |
| 하루 두 편 | `issue_runs` 의 `(user_id, ran_on) where ok` 유니크 인덱스 |
| 조용한 실패 | 성공이든 실패든 `issue_runs` 에 한 줄. 편집실 하단에서 보인다 |

## 8. 아직 안 한 것

- **노션 자동 동기화.** 지금은 0015 가 한 번 베껴온 것이다. 노션에서 관심사가
  바뀌어도 따라오지 않는다. 편집실에서 직접 추가·삭제하는 쪽이 더 빠르다고
  판단했다. 필요해지면 노션 API 로 주기 동기화를 붙인다.
- **이미지.** 자동 발행분에는 표지가 없다. 외부 이미지 호스트가 조직 정책에
  막혀 있어서, 사진 대신 활자가 지면을 끄는 지금 설계와도 맞는다.
- **발행 시각 조정 UI.** 지금은 워크플로의 cron 을 고쳐야 한다.
